# QA Quickstart for Shared Company Account Status

Run this scenario after the implementation tasks provide a service image, test identity issuer, and consumer builds. Use disposable PostgreSQL, MariaDB, and MySQL databases and synthetic account references in CI. Run the same migration, storage, and API conformance scenarios on all three. Use QA credentials through each runtime's existing provider setup only where testing an actual provider call is authorized. An account's credential is never transported by this feature.

## Setup

1. Deploy the service with one explicitly selected engine and a TLS-verified writer connection. Apply the matching migrations and verify readiness. Run the combined consumer walkthrough on the actual hosted pilot database. Configure one HTTPS origin and one approved issuer and audience for the pilot. Verify read, manage, and use permissions for two desktop operators, one Hermes identity, and two separate factory identities.
2. Publish a complete first grant revision. Register ten Claude accounts for the two desktop views. Link two local aliases to A, and a similarly named profile to a different account. Give Hermes and factory one access to A and B in the pilot environment using valid bindings. Give factory two access only to B. Ensure every consumer uses the same origin and canonical account references.
3. Open both desktop apps. Verify the initial Unknown view and absence of a saved revision. Initialize A and B to Active and set deliberate statuses for the remaining accounts. Verify A and B pass the local readiness checks for the consumers assigned to them. Record build and deployment pins and the grant revision.

## Database Acceptance

Test clean installation and upgrade where a previous schema exists. On every engine, verify case-distinct identifiers, grant withdrawal, concurrent first decisions, atomic audit and status writes, replay after uncertain commit, and visibility of an acknowledged pause from a separate service connection. Test interrupted migration recovery, including implicit DDL commits on MariaDB and MySQL. For each hosted configuration being qualified, exercise writer outage and failover. Confirm the service resumes on the recovered writer with acknowledged revisions intact, or remains unavailable while the operator reconciles state.

Capture scoped status reads, operation outcomes, and sanitized transition history. Include timestamps or operation IDs showing where admission occurred. Record the running-state and provider launch counts in the denied cases. Qualify every enabled runtime route for the pilot before marking the integration complete.
