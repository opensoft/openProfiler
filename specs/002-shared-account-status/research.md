# Research and Decisions

## Service and persistence

Use an openProfiler-owned hosted Rust HTTP service with a small storage interface for account reads, admission, transitions, and grant publication. SQLx provides typed PostgreSQL and MySQL/MariaDB drivers. Share common status rules in Rust and isolate driver SQL, migrations, and error translation. Shared behavior comes from the same conformance suite running on all three servers. One writer per deployment preserves a single order for committed decisions. [SQLx database support](https://github.com/transact-rs/sqlx#readme) · [PostgreSQL transaction isolation](https://www.postgresql.org/docs/17/transaction-iso.html) · [MariaDB transaction isolation](https://mariadb.com/docs/server/reference/sql-statements/transactions/set-transaction) · [MySQL transaction isolation](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)

Start with PostgreSQL 17 for the pilot and test MariaDB 11.4 LTS and MySQL 8.4 LTS independently. These are proposed qualification baselines. Managed offerings such as Aurora PostgreSQL and Aurora MySQL are worth qualifying when a deployment calls for them, using the corresponding driver and tests against the actual hosted writer and failover configuration. [PostgreSQL release support](https://www.postgresql.org/support/versioning/) · [MariaDB 11.4 LTS](https://mariadb.org/11-4-lts/) · [MySQL 8.4 release series](https://dev.mysql.com/doc/refman/8.4/en/mysql-releases.html) · [Amazon Aurora engines](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/)

Keep SQLite for possible local tooling. Hosted qualification requires the actual server engines and their transaction, migration, and failover behavior. Revisit SQL Server or Azure SQL only for an identified deployment that requires it. That would add a driver, dialect, and qualification matrix. [SQLite deployment guidance](https://www.sqlite.org/whentouse.html) · [SQLx database support](https://github.com/transact-rs/sqlx#readme)

## Desktop and workload identities

Use an explicitly configured, client-facing issuer per pilot environment. The openProfiler authority brainstorm identifies Keycloak for the family and permits Entra as its upstream. Use Keycloak if approved by the company's existing identity owners. The older broker proposal describes Entra directly and remains a proposal. Use the native system browser with authorization code and PKCE for desktops. Workloads authenticate with existing approved machine credentials for the service audience and a trusted subject-to-binding map. No pilot enrollment can proceed without that mapping and a current effective grant workflow. Considered treating identity provider membership as sufficient permission. The current account and factory bindings are more specific. [openProfiler authority brainstorm](../../docs/ideation/brainstorm/openprofiler-identity-persona-authority.md) · [OAuth 2.0 for Native Apps](https://www.rfc-editor.org/rfc/rfc8252.html)

## Effective grant publication

The xFactory credential registry template records an account reference per provider binding together with client, environment, host, persona, allowed factory instances, and roles. Independent effective bindings can yield multiple usable accounts. Keep the source binding shape intact. The controlled projection is a proposed pilot integration. A revision becomes effective when the service atomically applies it and its publisher acknowledges the result. Workflows responsible for changes and revocations use that ordering. Static release pins carry configuration provenance. The pilot needs a publisher that can report withdrawal and evidence of projection currency. [xFactory credential binding template](https://github.com/opensoft/xFactory-Agents-Credential-Registry/blob/c004d69/templates/credential-binding.yaml) · [Registry architecture](https://github.com/opensoft/xFactory-Agents-Credential-Registry/blob/c004d69/docs/architecture.md)

## Runtime evidence

FarHeap's deployment manifest describes a containerized Hermes gateway with local profiles. Use the pinned source and the configured messaging and API paths to find the final turn boundary. The upstream source paths in the plan are starting points. The xFactory-Hermes code claims a job before run creation. Omnigent has a separate inbox claim and direct launcher. Each installed runtime requires proof of where it starts the selected provider process or call, including any queue after its control-plane record. Considered polling once at worker startup or checking at initial dispatch. Either leaves stale decisions on queued work and persistent sessions.

Sources inspected include FarHeap/Hermes-Install's `k8s/prod/workloads/deployment/hermes-farheap.yaml`, xFactory-Hermes-Install's `src/hermes_install/api/routers/{jobs,runs}.py`, Omnigent-Install's `hermes_service/{dispatcher,launcher,server}.py`, and OmniWorker-Install's profile and preflight code. Installation pins and active runtime routes remain pilot setup inputs. ## Desktop compatibility and freshness

Use the existing native activation boundaries. Windows switch and undo stop a provider process and replace credentials, so managed admission must be checked first, against the exact target. Preserve local-only operation and its rollback file protection. For the first release, show dated results while the appropriate authenticated scope is current. Hide status when access or scope cannot be verified. Refresh on open and on demand. Treat failures explicitly and avoid an offline status store. Considered push notifications and admission from cached lists. A refresh plus the fresh decision meets the feature's timing and avoids admitting queued work against an old decision.
